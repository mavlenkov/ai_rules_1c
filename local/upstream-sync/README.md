# Проверка обновлений производителя

Python 3.8+ и Git; без сторонних Python-зависимостей. Linux (блокировка — стандартный `fcntl`). Запуск из корня репозитория:

```bash
# Один раз: явно задать проверенную принятую базу, не автоматически брать upstream HEAD.
python3 -B local/upstream-sync/upstream_sync.py accept --initialize 5700f54

# Обычная проверка; код 1 означает кандидата, а не сбой.
python3 -B local/upstream-sync/upstream_sync.py check

# После ручной интеграции и проверок источника — принять именно увиденную SHA.
python3 -B local/upstream-sync/upstream_sync.py accept <полная-SHA-из-сводки>
```

`check`: **0** — upstream совпадает с принятой базой; **1** — кандидат; **2** — ошибка (включая недоступный remote, смену identity, переписанную/неполную историю, отсутствие репозитория/базы, ошибочное состояние). `accept`: 0 — записано; 2 — отказ. Ошибки идут в stderr. Сетевые/Git-процессы ограничены 180 секундами каждый, интерактивный Git credential prompt отключён.

## Проверить одной командой

```bash
python3 -B -m unittest discover -s local/upstream-sync -p 'test_*.py' -v
```

Тесты полностью локальные, без сети, моделей, установок и исполнения кода производителя. Они создают временные Git-репозитории и проверяют кандидат/повтор/no-update, dirty/staged/untracked файлы и сырые байты index, переписанную историю, недоступный remote, identity/source drift, accept и ошибки состояния. Код 0 у этой команды означает успех всех тестов, а не отсутствие production-обновления.

## Конфигурация и состояние

`config.json` явно фиксирует `origin`, URL производителя и `main`. Несовпадение URL — отказ до fetch; автоматической смены identity нет. Можно указать `--repo <путь>` и `--config <путь>` **перед** подкомандой. По умолчанию репозиторий определяется относительно расположения скрипта, не текущего каталога.

Состояние: `<git-common-dir>/upstream-sync/state.json`, для обычного клона — `.git/upstream-sync/state.json`. Это локальный runtime-артефакт, не файл правил и не переносимый receipt установки. В linked worktree состояние и блокировка общие. Хранятся полные `accepted`, `seen`, `source`, identity, версия и один `candidate` с тройкой base/upstream/source-base. `source` — HEAD последнего успешного наблюдения/accept, **не** утверждение о проверках незакоммиченного дерева или установки. Установки/targets этим инструментом не учитываются.

Только `accept` создаёт/продвигает принятую SHA. Обычный accept требует точного совпадения с последней seen, неизменности source HEAD и наличия принятого коммита в истории source. Это ручное подтверждение владельцем уже выполненных проверок, не автоматический аудит семантики. `--initialize` действует только при отсутствии состояния и требует базу в истории source. Повторный check с теми же SHA не перезаписывает даже mtime состояния и не создаёт дополнительные кандидаты. Нет журналов уведомлений, сессий или временных меток; сводка печатается при каждом ручном вызове.

Запись атомарная, check/accept сериализованы файловой блокировкой. При ошибке сети, ancestry/identity или построения сводки JSON остаётся прежним. Fetch может обновить Git-объекты и FETCH_HEAD, включая ошибочный кандидат при переписанной истории; это не принятие. Пустой `--refmap=` отключает обновление ссылок из настроенного refspec, включая origin/main. Активная ветка, index и рабочее дерево не изменяются. Внешние Git hooks, diff/textconv, submodule recursion и автоматическое обслуживание отключены. Полученный контент только перечисляется; не импортируется и не исполняется.

## Проверено при реализации

- 14 локальных Git-тестов: PASS, включая неизменность всех файлов, сырых байтов index, HEAD и ссылок при dirty/staged/untracked данных.
- Реальный источник `49068b36f2fce3497747b8a472f4c2577a9cc438`: начальная база явно задана через `accept --initialize 5700f54`; check обнаружил `a624fcccb1950e0537c9031746986b685f045e59` и вернул **1** (4 коммита, 32 файла, +1352/−73).
- Повторный реальный check: **1**, JSON и mtime без изменений. Явный `accept a624fcccb1950e0537c9031746986b685f045e59`: **0**; следующий check: **0**. База после проверки — `a624fcc`, не `5700f54`.
- На реальном проходе сравнены хеши/режимы tracked и untracked файлов, сырые байты index, HEAD и все refs: без изменений. Ранее выполненная интеграция не повторялась; проверялось только состояние.
- Итоговое review: соответствие контракту 0/1/2, отказ до записи при ошибках, идемпотентность, блокировка/атомарная запись и отсутствие apply/model/install путей проверены; блокирующих замечаний нет. Это не проверка семантики правил производителя.

## Сводка и границы

Сводка содержит точные SHA, новые коммиты, файлы по областям, число файлов/добавлений/удалений и команду полного diff. Бинарные изменения отражаются в списке файлов; строковая статистика не измеряет их байты. Пересечения — совпадение путей upstream-diff и diff принятой базы с нашим committed HEAD; это не конфликт-анализ и не проверка пользовательских dirty-файлов. Сводка перечисляет затронутые каталоги адаптеров/экспортов, но не исследует установленные клиенты.

Нет checkout/merge/pull/reset/stash, push, PR, install, вызовов моделей и расписания. Начальное состояние нужно задавать заново в новом клоне. Не запускай инструмент с непроверенной Git-конфигурацией/credential helpers: стандартный Git transport использует локальные настройки авторизации. Точность принятия ручных source-checks остаётся ответственностью владельца.
